# Security

Signing identities decide whether future updates of an app can be installed, so losing one,
exposing one, or replacing one by accident is treated as a serious failure.

## Where data is stored

| Data | Location (Windows) | Contains secrets? |
| --- | --- | --- |
| Project profiles, settings | `%APPDATA%\HotAtticGames\BuildSigningManager\` | No |
| Logs | `…\BuildSigningManager\logs\` | No (secret values are also redacted defensively) |
| Signing identities | `%LOCALAPPDATA%\HotAtticGames\BuildSigningManager\vault\identities\<id>\` | Yes |
| Backups | Wherever you choose | Yes, encrypted |

Each identity folder holds:

- `identity.json`: public metadata (alias, certificate fingerprints, validity, backup history). No passwords.
- the keystore file itself.
- `credentials.bin`: keystore and key passwords, encrypted with **Windows DPAPI** for the current
  Windows user. Other Windows users on the same PC, or a copy of the file on another PC, cannot decrypt it.

Profiles reference identities only by id. The app never deletes identity folders or backups.

### Android

| Data | Location | Contains secrets? |
| --- | --- | --- |
| Project profiles | app-private `files/profiles/` | No |
| Signing identities | app-private `no_backup/vault/identities/<id>/` | Yes |

`credentials.bin` is encrypted with an AES-256-GCM key generated inside the **Android Keystore**
(hardware-backed where available, never exportable). App data is excluded from cloud backup and device
transfer, and `FLAG_SECURE` keeps secrets out of screenshots and the recent-apps preview. Keys are generated
with BouncyCastle (RSA 4096, SHA256withRSA) and stored as PKCS12 with PBES2/AES-256 key protection, which
current JDK keytool and Android build tools read. Existing JKS files are read with a reader for the
documented JKS format, and new keystores are always written as PKCS12. APKs are verified with Google's
`apksig` library.

## Key generation

- Keys are generated by the JDK's `keytool`: RSA 4096-bit, SHA256withRSA, PKCS12 keystore, valid about 27 years.
- Passwords are 32 characters from Python's `secrets` module (the operating system's cryptographic generator).
- PKCS12 keystores use one password for the store and the key, and the app says so.
- A new identity is only reported as created after the key has been unlocked and its certificate read back.
  If any step fails, the partial keystore is deleted so it cannot be mistaken for a valid identity.
- An existing keystore file is never overwritten. Replacing a project's identity requires typing `REPLACE`,
  and the old identity is kept.

## External tools

- Tools are found locally (JAVA_HOME, Android Studio, ANDROID_HOME, PATH, or Settings). Nothing is downloaded.
- Processes are started with argument lists, never through a shell.
- Passwords are passed through environment variables (`-storepass:env`, `--ks-pass env:`), never on
  the command line.
- Certificates are exported to standard output and parsed in memory, so no temporary certificate files
  are written. Recovery tests and restores write the keystore to a private temporary folder that is
  deleted straight afterwards.

## Clipboard

Secret values are copied only when you click a Copy button. On Windows they are marked so that clipboard
history and cloud clipboard ignore them. They are cleared after the configured delay and when the
application closes, but only if the clipboard still holds that exact value.

## Generated prompt

The prompt generator receives the project profile and the identity's *public* summary (alias and
fingerprint) only. It has no access to passwords or keystore bytes. Tests confirm that no secret value
appears in the prompt.

## Backups

### Backup format

```
HAGBSM-BACKUP 1\n
{JSON header}\n
<AES-256-GCM ciphertext>
```

- Header: `kdf` = `scrypt`, `n`, `r`, `p`, base64 `salt` (16 bytes), `cipher` = `AES-256-GCM`, base64 `nonce`
  (12 bytes), plus public labels (creation time, identity id and label, certificate fingerprint).
- Key: `scrypt(passphrase UTF-8, salt, n=131072, r=8, p=1)` → 32 bytes.
- Associated data: the magic line plus the header line, so any change to either is detected.
- Plaintext: a ZIP file containing `keystore/<file>`, `credentials.json`, `identity.json`,
  `manifest.json` (with the keystore's SHA-256 hash) and `RECOVERY.txt`.

The format uses only standard primitives from the `cryptography` package, with no custom cryptography.
`tools/decrypt_backup.py` decrypts it without the application.

### Verification

After writing a backup, the app reads the file back, decrypts it, checks the keystore hash, opens the
keystore with keytool using the stored passwords, and compares the certificate fingerprint. A backup is
marked **verified** only if all of this succeeds. **Test Backup Recovery** repeats the check at any time.

## Version 1.1 data handling

- Project and workflow inspection only **read** the linked folder; the manager never writes to a game project or repository and
  never contacts GitHub. Secret *names* found in workflows are stored; secret values are never read or stored from a repository.
- Profile import writes a verified backup to `migration_backups`, never modifies or deletes the source, never copies private
  signing material into profiles, and restores the previous state if a step fails.
- Changing platforms, identifiers, secret names or the workflow decision never regenerates, replaces or deletes a signing identity.

## Google Play and Apple data (unreleased additions)

- Upload keys live in the vault exactly like other identities (DPAPI-protected credentials, encrypted backups). Exporting the upload certificate writes only the public certificate, to a new file.
- Google's app-signing certificate and all Apple data are stored as public metadata in the profile. Entries typed or imported by the owner are labelled as such; nothing is verified against Google or Apple.
- Apple P12 files are opened in memory with a typed password to read public details. The private key and the password are not stored, logged or put in prompts; Python cannot guarantee that memory is wiped.
- Apple certificate/profile trust chains and signatures are NOT validated, and the app cannot prove a paid developer account or distribution rights.
- Exported profiles include this public metadata but never keys, passwords or P12 files.

## Limitations

- The vault protection relies on the Windows user account. Anyone signed in as you, or malware running as
  you, can use the identities. Keep the PC account secure.
- If Windows is reinstalled or the user profile is lost, DPAPI-protected credentials cannot be recovered.
  **Encrypted backups are the recovery path.** Keep at least one verified backup off this PC.
- Backups are only as strong as their passphrase. Use the generated passphrase or a long one, and store it
  separately from the backup.
- Android: uninstalling the app or clearing its data deletes the vault. Back up first.
- On non-Windows systems (development only) the vault uses a local key file instead of DPAPI, which is weaker.
- Windows Authenticode certificates and Apple certificates/provisioning profiles are not created or stored
  by this version. The app only explains what they require.
- The Android app is still version 1.0 and cannot open profiles that use version 1.1 features.
- The app does not connect to GitHub, so it cannot check whether secret names already exist.
- Without `apksigner`, APK checks can only read v1 (JAR) signature certificates and report them as unverified.

### Residual risks (reviewed for the Google Play / Apple expansion)
- DPAPI protects credentials only from other Windows users. Malware running as you can read them. A copy of the vault on another PC or account cannot be decrypted: restore from an encrypted backup there.
- Recovery depends on the backup passphrase; there is no escrow. Lose both the vault and the passphrase and the key is gone (for an upload key, Google offers a reset; for a direct key, installs can never update).
- Passwords briefly exist as ordinary Python strings and in child-process environments (keytool); redaction of logs is a second line of defence, not a guarantee.
- Windows Authenticode and Apple signing credentials are not stored by the manager; the manager records metadata only.
- Not independently audited. Passing automated tests is not evidence of commercial-grade security.
