# 2. PROJECT OBJECTIVE

Upgrade Hot Attic Games Build & Signing Manager from version 1.0.0 into a more intelligent, platform-aware project configuration and signing-management application.

The application should serve two purposes:

**New projects:** Generate appropriate identifiers, establish signing requirements, and produce accurate development instructions before the first build.

**Existing projects:** Discover and preserve existing identifiers, signing identities, build numbers, repository configurations, and saved project profiles.

The upgrade must support the application's selected platforms:

- Android
- Windows
- Linux
- iOS
- iPadOS
- macOS
- Web

Not every platform requires the same signing system, and some require no signing at all.

The application must adapt to the selected platforms rather than presenting Android signing as a universal requirement.

**This upgrade applies only to the Build & Signing Manager application. It must not modify the source code or release pipelines of any game without separate authorization.**

# 3. AUTOMATIC APPLICATION IDENTIFIER GENERATION

When creating a new project, the application must propose valid identifiers automatically.

Use the publisher and application name to generate a normalized reverse-domain identifier.

Example:

Publisher: `Hot Attic Games`

Application: `My Medieval Life`

Suggested identifiers:

| Platform | Identifier |
|---|---|
| Android | `com.hotatticgames.mymedievallife` |
| Apple | `com.hotatticgames.mymedievallife` |
| Desktop | `com.hotatticgames.mymedievallife` |

These are suggestions, not mandatory values.

Each platform's identifier must be independently editable.

Validate each identifier according to the requirements of its target platform.

Do not assume that every platform uses identical identifier rules.

### Development identifiers

Provide an optional separate development identifier.

Example:

`com.hotatticgames.mymedievallife.dev`

Do not automatically append `.dev` simply because the release channel is Private Testing.

Private testing and application identity are separate concepts.

Allow the owner to choose between using the eventual production identifier and maintaining a separate development identity.

Explain that a development identifier creates a distinct application identity.

### Identifier registry

Maintain a local registry of identifiers already assigned to projects within the manager.

Warn about duplicate identifiers across different projects on the same platform.

Allow the same identifier text across different platform ecosystems when valid.

Never silently modify identifiers to resolve conflicts.

# 4. EXISTING PROJECT IDENTIFIER DISCOVERY

When importing or linking an existing project, do not immediately generate replacement identifiers.

First, inspect available project configuration.

Where supported by the project engine or build artifacts, detect:

- Android package name.
- Apple bundle identifier.
- Desktop application identifier.
- Existing version.
- Existing build number or version code.
- Current target platforms.
- Existing signing configuration.
- Current release workflow configuration.

Use engine-specific inspection adapters where appropriate.

For Godot projects, inspect the relevant project and export configuration.

For other engines, use supported configuration readers rather than assuming Godot's file structure.

If an identifier cannot be determined reliably, leave it unresolved and request owner input.

Do not invent an existing identifier.

### Existing identifier changes

If the generated suggestion differs from the identifier already used by a game, show both values.

Explain that changing an Android package name or Apple bundle identifier can cause the operating system or store to treat the build as a different application.

Explain that desktop identifier changes can affect application data directories, shortcuts, and settings depending on the engine and packaging method.

Provide explicit options:

1. Keep the existing identifier.
2. Adopt the generated identifier after reviewing the consequences.
3. Enter a custom identifier.

Default to preserving the existing identifier.

Do not modify the game's actual configuration automatically.

Generate instructions for the development agent when a migration is approved.

# 5. PLATFORM-AWARE SIGNING REQUIREMENTS

The Signing Identities and GitHub Secrets screens must respond to the selected platforms and distribution requirements.

## Android

Retain the existing four default GitHub secret names:

- `ANDROID_RELEASE_KEYSTORE_BASE64`
- `ANDROID_RELEASE_KEYSTORE_PASSWORD`
- `ANDROID_RELEASE_KEY_ALIAS`
- `ANDROID_RELEASE_KEY_PASSWORD`

Preserve support for generating and backing up Android signing identities.

Continue supporting PKCS12 and compatible Android keystore formats.

Preserve certificate inspection, fingerprint reporting, and backup recovery testing.

Support distinct keystore and key passwords where the signing tool permits them.

Never assume those passwords match.

## Windows

Support optional executable code-signing configuration.

Do not require code signing for ordinary private Windows builds.

When Windows signing is enabled, identify the appropriate certificate, credential requirements, and signing workflow.

Do not treat Android keystores as Windows signing certificates.

## Linux

Ordinary native Linux builds must not require Android or Windows signing credentials.

Support additional signing requirements only when applicable to the selected distribution format.

## iOS and iPadOS

Support Apple bundle identifiers, signing certificates, provisioning profiles, and relevant distribution requirements.

Do not use Android keytool to generate Apple signing identities.

## macOS

Support appropriate Apple Developer ID signing and notarization configuration when applicable.

Keep macOS credentials separate from Android signing credentials.

## Web

Do not require application signing credentials for ordinary web builds.

Only request deployment credentials when a selected deployment workflow actually requires them.

### Interface behavior

Show only the credential requirements relevant to the selected platforms and signing methods.

Clearly distinguish:

- Required credentials.
- Optional credentials.
- Already configured credentials.
- Missing credentials.
- Credentials not applicable to the project.

Changing platform selections must never delete an existing signing identity or stored credential.

# 6. GITHUB SECRET-NAME COMPATIBILITY

GitHub secret names are references used by build workflows.

They are not signing identities.

The application must support configurable names instead of assuming every repository already uses its defaults.

### Required behavior

1. Propose standardized names for new repositories.
2. Preserve existing names when importing a repository.
3. Allow custom secret names.
4. Retain the existing numeric-suffix collision-avoidance option.
5. Never silently rename repository secrets.
6. Never overwrite existing secrets without explicit authorization.
7. Never regenerate signing identities to solve a secret-name mismatch.
8. Keep credentials isolated by repository.
9. Ensure generated Claude prompts use the actual configured secret names.
10. Explain when a workflow must be updated to use different names.

### Repository inspection

When the owner explicitly links a repository and authorizes inspection, read its existing build workflow configuration.

Identify which signing secrets the workflows reference.

Compare those names with the manager's configured names.

If they differ, offer:

**Option A: Adapt the workflow to the manager's existing secret names.**

**Option B: Configure the manager to use the workflow's existing secret names.**

**Option C: Custom mapping.**

Default to the option that preserves an existing valid signing identity and minimizes disruption.

Do not automatically commit repository changes.

If repository access is unavailable, generate precise instructions for Claude rather than claiming inspection was performed.

# 11. LOCAL IMPORT VERSUS CLOUD UPLOAD

The application must clearly distinguish local profile import from cloud synchronization.

**Cloud upload:** Sending project files or credentials to a remote service.

Local import is the required feature.

Do not automatically upload project files, signing keys, keystores, passwords, or backups to GitHub or any other remote service.

If cloud synchronization is proposed later, it requires a separate design and explicit authorization.
